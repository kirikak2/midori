# Tombola シーケンサー

回転する多角形の中でボールが跳ね、壁に当たった瞬間にノートを発音する物理
シミュレーション型シーケンサー。グリッドに乗らない、非周期的で有機的なリズムを
作るためのもの。

- 実装: [main/ui/screen_tombola.cpp](../main/ui/screen_tombola.cpp)（物理・描画・発音）
- Ruby API: `UI::Tombola`（[mrbgems/picoruby-ui/mrblib/ui.rb](../mrbgems/picoruby-ui/mrblib/ui.rb)）
- 対応ボード: M5Stack CoreS3 / M5Stack Tab5（画面が必要）。Freenove ではすべて
  no-op（[main/platform/platform_freenove.c](../main/platform/platform_freenove.c) のスタブ）

## 構成

```
 [PicoRuby task]                    [UI task (app_main, 10ms周期)]
  UI::Tombola                        ui_update()
    └ UI._tombola_set_i(:sides, 8) ──→ g_model (mutex)
                                        └ ui_tombola_tick()
                                            ├ 物理ステップ
                                            ├ 衝突 → MIDI_Note_trigger()   ← 発音はここ
                                            └ 衝突 → ui_event_push()       ← notify時のみ
    UI.process ←─────────────────── イベントキュー
      └ on_hit ブロック
```

**発音は C++ 側が担当する。** 衝突を検出した同じフレームで
`MIDI_Note_trigger()`（既存のノートスケジューラ）を呼ぶので、ノートのタイミングは
スクリプトが `UI.process` をどれだけ細かく回すかに依存しない。`on_hit` を登録すると
同じ衝突が Ruby にもキュー経由で届く（表示・記録用）。Ruby だけで鳴らしたい場合は
`t.sound = false` で C++ 側の発音を切る。

`ui_tombola_tick()` は現在の画面に関係なく `ui_update()` から毎回呼ばれる。
Tombola 画面から離れても演奏は止まらない。

## 座標系

物理は**正規化座標**で計算する。多角形の外接円半径を 1.0、原点を中心とし、
ピクセルへの変換は描画時にのみ行う。これにより 320x240 の CoreS3 と 1280x720 の
Tab5 で**まったく同じ挙動**になる（速度・重力・ボールサイズはすべて「外接円半径/秒」
などの単位）。

描画レートはボードで変える（Tab5: 約30fps / CoreS3: 約20fps）。この画面で
一番高いのはプレイエリアの押し出しで、ボールのサイズを考えるとこれ以上
上げても見た目はほとんど変わらない。**物理ステップはどちらも 10ms のまま**なので、
描画レートを変えてもノートのタイミングは変わらない。

## Ruby API

```ruby
require 'midi'
require 'ui'

t = UI::Tombola.new(sides: 6, rotation: 12, gravity: 0.5,
                    device: MIDI::Device.new(MIDIDevices.sam2695))
t.scale = [36, 38, 42, 45, 46, 49]
t.add_ball(color: :red)
t.start
t.show
```

C++ 側の状態はグローバルなシングルトンなので、**Tombola は同時に 1 つ**。
`Tombola.new` は既定値にリセットしてから引数を適用する。

### パラメータ

| メソッド | 既定値 | 範囲 | 内容 |
|---|---|---|---|
| `sides` | 6 | 3〜16 | 多角形の辺の数。音列の長さでもある（辺 N → `scale[N % scale.size]`） |
| `rotation` | 12.0 | -600〜600 | 回転速度 RPM。負で逆回転 |
| `radius` | 0.85 | 0.2〜1.0 | 描画サイズ（画面に対する比） |
| `gravity` | 0.5 | 0.0〜4.0 | 重力の強さ |
| `gravity_mode` | `:down` | `:down` `:center` `:none` | 下向き／中心引力／無重力 |
| `bounce` | 0.8 | 0.0〜1.2 | 反発係数。壁とボール同士の両方に効く。1.0 超で跳ねるたびに加速する |
| `friction` | 0.99 | 0.0〜1.0 | 接線方向の減衰（1.0 で摩擦なし） |
| `spin_transfer` | 0.3 | 0.0〜1.0 | 衝突時にボールの接線速度を壁の速度へどれだけ引き寄せるか。1.0 で壁の速度そのものになる。**0 にすると重力ありのパッチは底に溜まって鳴らなくなる** |
| `ball_size` | 0.05 | 0.005〜0.4 | ボール半径（多角形に対する比） |
| `scale` | `[36,38,42,45,46,49]` | 最大16要素 | 辺 → ノート番号 |
| `channel` | 9 | 0〜15 | 既定 MIDI チャンネル（GM ドラム） |
| `duration` | 120 | 1〜10000 | ノート長 ms |
| `velocity_range` | `[16,127]` | 1〜127 | 衝突速度をこの範囲へマップ（後述） |
| `retrigger_ms` | 30 | 0〜5000 | 同じボールの連続発音の最小間隔 |
| `max_voices` | 8 | 1〜16 | 1ステップあたりの最大発音数 |
| `sound` | true | — | C++ 側で発音するか（`sound?` で参照） |
| `touch_add` | true | — | 多角形の内側をタップしてボール追加（`touch_add?` で参照） |
| `device` | — | — | 出力先。`MIDI::Device` かトランスポートを渡す |

すべて実行中に変更できる。エンコーダやパッドに割り当てるのが本来の使い方：

```ruby
UI.pad(1, label: "Faster") { t.rotation = t.rotation + 4 }
UI.pad(2, label: "Sides+") { t.sides = t.sides + 1 }
```

### ボール

```ruby
t.add_ball                                    # scale から音程、既定 ch
t.add_ball(note: 36, channel: 9, color: :red) # 固定ノート（ドラム用）
t.add_ball(velocity_scale: 0.7)               # このボールだけ弱く
t.balls          #=> 現在の個数
t.balls = 5      # 個数を合わせる
t.remove_ball(0)
t.clear_balls
```

最大 16 個。`add_ball` は空きがなければ `-1` を返す。
`note:` を省いたボールは当たった辺で音程が決まり、`note:` を与えたボールは常に
その音を鳴らす（辺とボールのハイブリッド）。

### ボール同士の衝突

ボール同士も弾性衝突する（質量は等しく、反発係数は壁と同じ `bounce`）。
**ボール同士の衝突ではノートは鳴らない** — 楽器はあくまで多角形の辺。

これが無いと、頂点に集まったボールが重なったまま動かなくなり、その後の変化が
止まってしまう。処理は「重なりを半分ずつ押し戻してから法線方向の力積を等分」で、
1 ステップあたり最大 120 ペアだが実際に接触しているものだけ計算する。

### 衝突強度とベロシティ

壁への接触は**弱いものが圧倒的に多い**。既定パッチを 6 分ぶんシミュレートすると、
接触の 51% が 0.15 未満、91% が 0.5 未満（単位は外接円半径/秒）だった。落ち着き
かけたボールは、法線速度をどんどん小さくしながら壁を何度も叩き続けるため。

そこで:

- **0.15 未満の接触はノートを鳴らさない**（物理的な解決だけ行う）。これらは
  「衝突」ではなく擦れなので、以前はここが全部 velocity 40 で鳴っていた
- 0.15〜3.0 を `velocity_range` へ線形にマップする。99.9% の衝突が 3.0 未満
- 既定の下限を 40 → **16** に下げた。40 は「一番弱い音」としては大きすぎた

結果（既定値の場合）:

| 衝突速度 | 0.10 | 0.20 | 0.40 | 0.80 | 1.50 | 2.50 | 3.50 |
|---|---|---|---|---|---|---|---|
| 旧 | 40 | 40 | 44 | 53 | 69 | 92 | 115 |
| 新 | 無音 | 17 | 25 | 41 | 68 | 107 | 127 |

### 衝突の受け取り

```ruby
t.on_hit do |hit|
  # hit => {ball: 0, side: 3, note: 45, velocity: 96}
  UI.log("side #{hit[:side]} note #{hit[:note]}")
end

loop do
  UI.process   # ← これを回さないとブロックは呼ばれない
  sleep_ms 5
end
```

`on_hit` を登録すると C++ 側の通知フラグが立ち、衝突が UI イベントキューへ流れる。
キューは有限なので、`UI.process` を回さないまま放置すると溢れて捨てられる（音自体は
C++ 側が鳴らすので影響しない）。

### 開始・停止

```ruby
t.start      # ボールが 0 個なら 3 個スポーンする
t.stop
t.running?
t.reset      # 全パラメータを既定値に戻し、ボールを全消去
t.show       # Tombola 画面へ切り替え
```

画面下部の中央ナビボタンが `Start` / `Stop` になっている。

## 画面

- 多角形: 実行中はシアン、停止中はグレー
- 直前に当たった辺が約 90ms 白く光る
- プレイエリア左上に `N6 12rpm G0.50 B0.90 x3`（辺数 / 回転 / 重力 / 反発 / ボール数）
- 多角形の内側をタップするとその位置にボールが増える（`touch_add`）

### ドラッグで回す

画面に触れている間、多角形の回転は**指の動きだけ**に従う（`rotation` パラメータは
無視される）。指を止めれば多角形も止まり、離すとパラメータの値で回転を再開する。
再開位置は指が置いていった角度から。

**多角形は指が中心まわりに掃いた角度ぶんだけ、厳密に回る。** 指の下にある頂点は
指の下から動かない。実物の車輪の縁を掴んで回すのと同じ。

```
dragRotate((px * dy - py * dx) / r2);   // px,py = 中心からのオフセット, r2 = px²+py²
```

これは `d(atan2(py, px))` そのもの。だから「だいたい合う」ではなく**厳密に一致**し、
距離にも経路にも依らない。

| 指の動き | 画面の左側 | 画面の右側 |
|---|---|---|
| 上へ | 時計回り | 反時計回り |
| 下へ | 反時計回り | 時計回り |

| 指の動き | 画面の上側 | 画面の下側 |
|---|---|---|
| 左へ | 反時計回り | 時計回り |
| 右へ | 時計回り | 反時計回り |

- **中心から遠くを持つほど、同じ移動量に対する回転は小さくなる**。細かく合わせたい
  ときは外側を持つ
- 円を描くように動かせば、そのぶん何周でも回り続ける
- **中心付近は分母をクランプする**（`DRAG_MIN_RADIUS`＝半径の 20%）。r² で割るので、
  クランプが無いと中心から 5px の位置で 20px 動かしただけで 229° 回ってしまう。
  クランプの内側では厳密追従ではなくなり、中心ちょうどでは回転 0 になる
- ドラッグ中は指の角速度がそのまま壁の速度になるので、`spin_transfer` を通して
  ボールも振り回される。フリックすると弾ける
- 指の速さは `MAX_DRAG_OMEGA`（12 rad/s）で頭打ちにしている。衝突の解決が
  破綻しない範囲に収めるため
- 停止中でもドラッグで多角形は回る（ボールは動かない）
- **タップとドラッグの区別は指を離した時点で行う**。`TAP_SLOP` ピクセル以上
  動いていればドラッグ、そうでなければタップとしてボールを追加する。同じ指で
  両方を使い分けられるようにするため

実装には `Screen::onTouchMove()` を新設した（既定は no-op なので他の画面に影響は
無い）。あわせて、**離した時のイベントは「押し始めた場所」で判定する**ように
変更した。従来は「離した瞬間の座標」がコンテンツ領域内かで判定していたため、
ナビバーまで指を滑らせて離すと画面に通知が届かず、ドラッグが終わらない（パッドなら
押しっぱなしになる）。

### ダブルバッファリング

プレイエリア（コンテンツ領域に収まる最大の正方形）全体をオフスクリーンで組み立ててから
パネルへ転送する。直接パネルへ描くと「線と円を消してから描き直す」ことになり、
その中間状態がそのまま見えてちらつく。

- バッファは画面ごとに持たず、**UI 全体で共有する帯（ストリップ）バッファ**
  （[main/ui/ui_strip.h](../main/ui/ui_strip.h)）を使う。プレイエリアを横長の帯に分けて、
  帯ごとに「黒で塗る → 描く → 転送」を繰り返す。Tab5 では幅 620 × 132 行ずつ 5 帯
- 以前は 620x620（≈ 768KB）のスプライトを持っていたが、内部 RAM に入らず PSRAM に
  落ちて描画が遅かった（2026-10-12 に共有ストリップへ移行）
- 帯ごとに `renderFrame()` を呼び直す（はみ出した部分は LovyanGFX がクリップする）。
  モデルのスナップショット（`TombolaFrame`）は 1 フレームに 1 回だけ取り、全帯で
  同じものを使う。帯ごとに取り直すと、帯の境界をまたぐボールがずれて描かれる
- 帯の中身はフレームをまたいで残らないので、毎フレーム全体を描き直す
  （前フレームの線と円だけを消す差分消去は、直接描画のフォールバック専用になった）
- ストリップを確保できなかった場合は、直接パネルへ「前フレームを消してから描く」方式に
  フォールバックする（ちらつくが動く）
- HUD もプレイエリアの中に描く。同じバッファに載せないと、そこだけ別タイミングで
  更新されて単独でちらつくため
- 停止中は「表示に出る値」が前フレームと同じなら描画自体を飛ばす。止めた
  Tombola 画面を開きっぱなしにしてもコストがかからない

### フレームバッファへの直接コピー（Tab5 / CrowPanel）

Tab5 のパネルは**フレームバッファパネル**で、LovyanGFX は MIPI-DSI が
そのまま走査する PSRAM 上のバッファへ直接描く。バス転送は無い代わりに、
`pushSprite()` は [Panel_FrameBufferBase::writeImage()](../managed_components/m5stack__m5gfx/src/lgfx/v1/panel/Panel_FrameBufferBase.cpp)
でのコピーになる。しかも**回転が入っているので `memcpy` の速い経路にすら乗らない**
（`writeImage()` が `memcpy` を使うのは回転 0 のときだけで、それ以外は 1 画素ずつ
回転付き `pixelcopy` を通る）。プレイエリアなら毎フレーム 384,400 画素。

[main/ui/ui_fb.cpp](../main/ui/ui_fb.cpp) が帯をフレームバッファへ CPU で直接コピーする。

- LovyanGFX の画素の写し方（`drawPixelPreclipped()`）はすべてアフィンなので、
  画面座標 (X, Y) のバッファ添字は `base + X*dX + Y*dY` になる。回転ごとの
  `dX` / `dY` / `base` はこの式から求める（全回転で式と一致することを確認済み）
- Tab5（rotation 3）では `dX = -720`、`dY = 1`。帯の 1 列がフレームバッファの
  1 行の連続区間になる。32 列ずつのタイルで行を内側に回し、同時に触る
  フレームバッファの行を 32 本に抑える
- コピー後に触った範囲を `esp_cache_msync(C2M)` で**書き戻すだけ**（invalidate は
  しない）。LovyanGFX がまだ書き戻していない描画を消さない
- フレームバッファのアドレスは `Panel_DSI::config_detail().buffer`（public）から取る

**座標系に注意（以前これで画面が化けた）**: フレームバッファは
`config().panel_width/panel_height` = **720x1280 の縦長**で、1280x720 は
`setRotation(3)` 後の論理座標。ストライドはパネル側の幅で計算する。
`offset_rotation != 0` の場合は `_internal_rotation` が `getRotation()` と
一致しなくなるのでフォールバックする。

**バイト順にも注意**: スプライトは `rgb565_2Byte`（バイトスワップ有り）、Tab5 の
パネルは `rgb565_nonswapped`。両者が違うときは 1 画素ずつ `bswap16` する。

### PPA をやめた理由（2026-10-12）

2026-08 から 2026-10 までは、この転送を ESP32-P4 の PPA（Pixel-Processing
Accelerator）の `ppa_do_scale_rotate_mirror()` で行っていた。入力が PSRAM の
620x620 スプライト・1 フレーム 1 回の転送では問題なかったが、共有ストリップに
移行して**入力が内部 RAM・1 フレーム数回の帯転送**になったところ、しばらく動かすと
**トランザクションが完了しなくなる**ようになった。直前まで何度も成功していた
同じジオメトリ（620x132, rotation 3）で起き、エンジンは実行中に復旧できない。
`PPA_TRANS_MODE_BLOCKING` は `portMAX_DELAY` で待つので、UI タスク（= Tombola を
進めるメインタスク）ごとフリーズしていた。原因（シリコン側の条件）は未特定なので、
決定的に動く CPU コピーに置き換えた。

PPA 時代に踏んだ問題（git 履歴に詳細あり）:

- PPA ドライバは DMA 後に出力ウィンドウを invalidate するが、それは**ブロックが跨ぐ
  パネル走査線の全幅**。LovyanGFX がまだ書き戻していないステータスバー等の描画が
  捨てられ、画面が乱れた（2026-08-10。ブリット直前の `M5.Lcd.display()` で対処していた）
- トランザクションプールが 1 個だと、同じ周回の 2 回目のブリットが空振りした

## ロータリーエンコーダから操作する

[examples/tombola.rb](../examples/tombola.rb) は DFRobot Visual Rotary Encoder
(SEN0502) を最大 4 台まで自動検出して、Knobs 画面のノブ 4 個に割り当てる
（[docs/KNOBS.md](KNOBS.md) の「ロータリーエンコーダから動かす」と同じ形）。
値を実際に変えているのは各ノブの `UI.knob` ブロックで、エンコーダは
`UI.knob_set` 経由でその値を書き込むだけ。

| 台目 | I2C アドレス | ノブ | 回すと | クリックすると |
|---|---|---|---|---|
| 1 | 0x54 | Rotation | `rotation`（-60〜60 rpm） | `add_ball` |
| 2 | 0x55 | Sides | `sides`（3〜16） | `clear_balls` |
| 3 | 0x56 | Gravity | `gravity`（0.0〜2.0） | オクターブ -1 |
| 4 | 0x57 | Bounce | `bounce`（0.0〜1.2） | オクターブ +1 |

- 検出はアドレス順。繋がっていない分は飛ばされ、0 台でもスクリプトは動く
  （その場合はパッドとノブのタッチ操作だけで演奏する）
- オクターブシフトは `scale` をまるごと ±12 半音して入れ直す。1 音でも 0-127 を
  外れる場合はシフトしない（端の音だけクランプすると音列の形が崩れるため）
- 起動時と、Knobs 画面でノブをタッチで動かしたとき（`UI.on(:knob_change)` の
  `final:` を見て）に、現在値をエンコーダのカウンタへ書き戻す（LED リングと
  ノブ位置が実際の値を指すようにするため）
- ボタンは「押下でフラグを立てて読んだらクリア」方式で 1 クリックでも複数回
  立つので、エッジ検出＋300ms のロックアウトで 1 回に落としている
- パッドは Ball+ / Clear / Octave- / Octave+ の 4 つのみ。rotation / sides /
  gravity / bounce はノブ（画面タッチまたはエンコーダ）でのみ操作する

**出力は常に USB-MIDI デバイス（USB-C）。** エンコーダの有無に関わらず
`MIDIDevices.usb_midi_device` を使うので、Tab5 で Port A (53/54) をエンコーダに
使っていても（SAM2695 の UART と同じピンで競合するので）配線の悩みが増えない。

## 浮動小数演算について

`-ffast-math` は**使っていない**。[main/CMakeLists.txt](../main/CMakeLists.txt) で
`main` コンポーネントに `-fno-math-errno` だけを付けている。

理由は実測。`ui/screen_tombola.cpp` を各フラグでコンパイルして比較した結果:

| フラグ | .text | `fsqrt.s` | libm 呼び出し |
|---|---|---|---|
| 既定 | 12848 | 0 | 15 |
| `-fno-math-errno` | 12744 | 4 | 11 |
| `-ffast-math` | 12546 | 3 | 11 |
| `-Ofast` | 17474 | 5 | 15 |

既定では `sqrtf` が**ライブラリ呼び出し**になる（`-fmath-errno` が既定で、負の値に
対して errno を設定する必要があるため FPU の `fsqrt.s` にできない）。
`-fno-math-errno` を付けるとハードウェア命令になる。`-ffast-math` はそこから先を
ほとんど改善しない — 残っている呼び出しは `cosf`/`sinf` で、これはどちらにせよ
インライン化されないため。

**そもそも浮動小数演算はボトルネックではない。** 三角関数の呼び出しは
1 ステップあたり 13 回（`sides=6`）+ 描画で 1 フレーム 28 回程度、合計しても
毎秒 2000 回強で、CPU 時間の 0.1% に届かない。重かったのはプレイエリアの
押し出しで、そちらは PPA へ移した。

`-ffast-math` を避けているのは、得るものが無いわりに `-ffinite-math-only` を
含み、リンク時に FPU をプロセス全体で flush-to-zero に切り替えうるため。

## 初版に入れていないもの

- **`quantize`**: 衝突を BPM グリッドへスナップさせる機能。発音を遅延キューに
  載せる必要があるため見送り
- **`gap`**: 辺の 1 つに穴を開けてボールが出入りする版
- 複数 Tombola の同時実行（C++ 側の状態がシングルトンのため）

## 既知の制約

- ボールが壁に沿って転がると `retrigger_ms` の間隔で鳴り続ける。うるさい場合は
  `retrigger_ms` を上げるか `bounce` を上げて転がらせない
- `bounce` を 1.0 より大きくすると系にエネルギーが入り続け、最終的に速度クランプ
  （8 半径/秒）に張り付く
